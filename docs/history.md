## 1. 仕様策定

### 調査したこと

- **支給要件** `doc/app-spec.txt` — 3 つの課題（覚えた≠使える／間違えた理由が不明／続けても実感なし）への回答が求められていた。
- **単語データ** `doc/toeic_wordlist.xlsx` — 300 語、7 列。難易度は L1:40 / L2:110 / L3:150。全語に「混同しやすい類似語」があり、これが誤答分析の判断材料になると判断した。
- **参考デザイン** `KouxaPlatform_2` — 桜色がかった白背景・ローズピンク・大きな角丸・ピル型ボタン・真っ黒を使わない、というトーンを抽出した。

### 決めたこと

アプリ名は **700 Lab**、タグラインは「今日の15分が、700点をつくる。」。3 課題それぞれに機能で回答する構成にした。

| 課題 | 回答 |
|------|------|
| 覚えた≠使える | 1 語を「認識」「運用」の 2 段階で管理。意味の 4 択に正解しても `recognized` 止まりで、文脈穴埋めに正解して初めて `using` に昇格する |
| 理由が不明 | 不正解時に Gemini が 4 タイプ（類似語混同／品詞ズレ／記憶あいまい／文脈読み違い）に分類 |
| 実感がない | 700 点メーター（推定到達スコア）を算出し、セット終了時に差分で提示。計算式はアプリ内で公開 |

**差別化点**として、誤答カルテを「見せて終わり」にせず、最頻誤答タイプによって**選択肢のダミー生成ロジック自体を変える**設計にした。分析 → 出題への還元ループがこのアプリの核となる。

### 判断が必要だった点

- **フォント** — 技術構成の指定は Fraunces / Space Mono のみだが UI の大半が日本語のため、日本語本文用のフォント追加を検討した（後にサイズ問題で不採用。§2 参照）。
- **API キーの置き場** — ログイン・サーバーなしの構成上、キーは端末側に置くほかない。学習・デモ用途である旨を設定画面に明記する方針とした。

## 2. 実装

### 環境構築でつまずいた点

- `create-expo-app` のテンプレートが **SDK 57** だったため、仕様の **SDK 54** に合わせて `package.json` を手書きし、`npx expo install` で互換バージョンを解決した。
- `jest-expo` / `babel-preset-expo` も最新の 57 系が入ってしまい、テストが `clearMocksOnScope is not a function` で起動しなかった。**54 系に固定**して解消。この教訓は CLAUDE.md に記録した。

### 仕様変更 1: 日本語フォントの不採用（spec v1.1）

`@expo-google-fonts/zen-maru-gothic` は **1 ウェイト 3.8MB** あり、起動時間要件（3 秒以内）を満たせないと判断して不採用にした。日本語は OS 標準フォントを使う。結果として、元要件のフォント指定どおりの構成に戻った。

### 単語データの変換

`doc/toeic_wordlist.xlsx` → `src/data/toeic_wordlist.json` の変換スクリプトを、**追加依存なし**で実装した（`xlsx` パッケージは既知の脆弱性があるため回避し、ZIP + inlineStr を自前でパース）。変換時に件数・レベル分布・必須項目の欠損を検証して落ちるようにしてある。

### 仕様変更 2: スコア式の再調整（spec v1.2）

当初のレベル重み（L1 0.55 / L2 0.85 / L3 1.15）では、全語習得時に **766 点**になり「700 点に到達する設計」と合わなかった。実データの分布に合わせて **0.45 / 0.70 / 0.89** に調整し、≒701 点に収めた。

### 仕様変更 3: 類似語ダミーの適用範囲（spec v1.2）

実データを測ったところ、`similar` 列の 860 語のうち単語マスタ 300 語に実在するのは **101 語**だけだった。このため:

- **`use` 形式**（英単語 4 択）は `similar` の文字列をそのまま使えるので**全 300 語で成立**する
- **`recognize` 形式**（日本語の意味 4 択）は類似語の和訳が必要なので、master 内に実在する語（順方向 + 逆引きで 109 語）に限られ、それ以外は同品詞・同レベルへ劣化フォールバックする

混同対策の主戦場は `use` 形式である、と仕様に明記した。

### デザイン

`frontend-design` を読み込んだうえで、シグネチャを **「二層ゲージ」** に定めた。進捗表示をすべて〈認識＝淡い層〉と〈運用＝濃い層〉の 2 層で描き、**その差自体がこのアプリの主張**になるようにした。ホームのアーチゲージ、単語帳の行インジケータ、進捗タブのバーで一貫して使っている。誤答フィードバックは「カルテ（診断票）」として、破線枠のカードで提示する。

## 3. 検証と修正（1 回目）

Web で実際に動かして通し確認した結果、ユニットテストでは出ない不具合が見つかった。

| 症状 | 原因 | 対応 |
|------|------|------|
| **回答が消える** | AI 応答の解決後に回答を記録していた。仕様上「待たずに次へ進める」ため必ず起きる | タップ時点で同期的に記録・永続化し、誤答タイプだけ後追いで追記する構造に変更 |
| **連打で二重登録**（10 問セットが 11 問に） | `chosen` の state 参照は次のレンダーまで更新されず、同一フレームの 2 回目を止められない | ref でガード |
| フォールバック時の誤答タイプが常に「記憶があいまい」 | 意味選択では選択肢が日本語なのに、英語の類似語リストと突き合わせていた | 選ばれた意味から語を逆引きし、類似語・品詞・場面で判定 |
| 誤答カルテの百分率が 63% + 38% = 101% | 各値を独立に四捨五入していた | 最大剰余法で合計を 100% にそろえる |
| 進捗ゼロでゲージに点が残る | 線端の丸みだけが描画されていた | 到達 0 の層は描画しない |

この経験から、CLAUDE.md に「**画面を変更したら実際に動かして目で確認する**」というルールを設けた。

## 4. 「問題が日本語で出力されている」の修正（spec v1.4）

### 原因

**Chrome のページ自動翻訳**だった。Expo の Web ビルドが既定で `<html lang="en">` を出力するため、日本語環境の Chrome が「英語ページ」と判定してページ全体を日本語に翻訳し、**出題対象の英単語まで置き換えていた**（`schedule` →「スケジュール」、`customer` →「顧客」）。単語データ自体は最初から英語で、表示層の問題だった。

### 対応

ルート HTML を `lang="ja"` + `translate="no"` + `<meta name="google" content="notranslate">` にした。`app/+html.tsx` は静的書き出し時にしか効かないため、`app/_layout.tsx` で実行時にも適用している。

### あわせて修正

AI 不通時のフォールバック例文が品詞を無視した固定文で、名詞に当てると `We need to review the customer before the meeting.`（顧客をレビューする）という不自然な英文になっていた。**品詞別テンプレート**（動詞／名詞／名詞句／形容詞／副詞）に変更し、自分で書いた文の英文法ミス（`before tomorrow morning meeting` → `before the meeting tomorrow morning`）も直した。

### この時点で判明したこと

実 API キーが設定済みで、**Gemini のライブ連携が動作していた**。誤答分析の品質も設計どおりだった。

> 「実演する・証明する」という回答は、present が持つ「発表する」という意味合いから連想されたのかもしれませんね。しかし、これは 'demonstrate' や 'show' といった…単語と混同している可能性が高いです。 — 誤答タイプ: `類似語の混同`

## 6. 再検証（spec v1.5）

CLAUDE.md の手順に従って再検証した。

### 不具合: 前の問題の解説が次の問題に表示される

5 問目 `contact` の画面に、4 問目 `available` の解説が出ていた。AI 応答が遅れて返ったとき、**すでに次の問題へ進んでいても、その結果を今の問題の解説として表示**していた。仕様上「待たずに次へ進める」ことを認めているので必ず起きる。回答時の問題番号を保持し、解決時に一致しなければ破棄するよう修正（MT-UI-16 としてテスト仕様に追加）。

### 発見: Gemini 無料枠は 1 日 20 リクエスト

総括だけが毎回フォールバックになるため 429 の内訳を調べたところ、こうだった。

```
quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier
value:   20
```

当時の設計は 1 セットで **12 リクエスト**（問題文生成 1 + 各問 10 + 総括 1）消費していた。つまり無料枠では **1 日 1.6 セット**しか回せず、最後に呼ぶ総括（AC-06）から先に落ちる。日次上限なので待っても回復しない。

コード欠陥ではないため、確実に正しい範囲だけ先に直した。

- 429 を「分あたり（待てば回復）」と「1 日あたり（待っても無駄）」に区別
- 分あたりの制限は総括に限り最大 35 秒待って再試行
- 理由別の案内文（キー未設定／分制限／日次上限／通信エラー）と、総括の再取得ボタンを追加

消費回数そのものの削減は**呼び出しタイミングの仕様変更**にあたるため、選択肢を提示してユーザーの判断を仰いだ。

## 7. API 消費削減（spec v1.6）

ユーザーの承認を得て、次の設計に変更した。

| タイミング | 変更前 | 変更後 |
|---|---|---|
| セット開始 | 運用形式の語だけ穴埋め文を生成（1 回） | **全 10 語**の例文・和訳・勘所・見分け方＋穴埋め文を**まとめて 1 回**で生成 |
| 各問の回答 | 正誤にかかわらず毎問 1 回（10 回） | **不正解のときだけ** 1 回。正解時は API を呼ばない |
| セット終了 | 総括 1 回 | 変更なし |
| **合計** | **常に 12 回** | **1 + 誤答数 + 1 回** |

誤答分析だけは「ユーザーが実際に選んだ答え」が事前に分からないため、都度の呼び出しを残した。

### 実測

10 問中 6 問誤答のセットで **8 回**（= 1 + 6 + 1）。旧設計なら 12 回。正解率 70% なら 5 回で、無料枠でも **1 日 4 セット**回せる。全問誤答なら 12 回で旧設計と並ぶが、**正答率が上がるほど消費が減る**構造になっている。

正解時の表示も実 API で確認した。`order` に正解した画面では、追加の呼び出しなしに勘所（`request` との違い）とビジネス例文（購買・在庫）が出ている。

### トレードオフ

セット開始時に 10 語ぶんをまとめて生成するため、開始待ちが数秒長くなる。また 1 回の失敗で全語がテンプレートに落ちるが、品詞別テンプレートを用意済みで学習自体は成立する。

## 振り返り

ユニットテストは 89 件通っていたが、**実際に動かして初めて見つかった不具合が 10 件中 7 件**を占めた。回答の消失・連打の二重登録・前問の解説の混入は、いずれも「非同期処理と画面遷移が絡む」場所で起きており、純粋関数のテストでは原理的に検出できない。CLAUDE.md に「画面を変更したら実際に動かして目で確認する」を必須ルールとして残した理由がこれである。

また、API の無料枠という**外部制約が設計そのものを変えた**点も記録に値する。「毎問 AI に問い合わせる」という素直な設計は、1 日 20 リクエストの前提では成立しなかった。制約を測ってから設計を選び直すという順序が、この件では有効だった。
